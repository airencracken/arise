# Arise Capability Audit — 2026-07-16

## Purpose

This document is the current behavioral baseline for Arise. It supersedes any
older audit statement that describes Arise as having full emerge parity.

Arise is intended to become a real competitor to Portage's `emerge`, while
retaining its existing design goals:

- a statically linked Go control plane that remains useful when Python is broken;
- deterministic, indexed package metadata rather than repeated filesystem scans;
- aggressive concurrency where dependencies permit it;
- substantially faster queries, planning, fetching, and builds;
- filesystem state as the source of truth;
- a pragmatic Bash subprocess boundary for ebuild and eclass execution;
- one coherent tool for emerge, eix, equery, and common recovery operations.

Feature parity is necessary but not sufficient. Arise is not successful if it
is merely a compatible rewrite or a slightly faster emerge. Its architecture
must deliver a large, reproducible speed advantage in normal use while
preserving complete behavioral compatibility. Performance is therefore a
design constraint and release gate, not a final optimization phase.

No CLI option is considered implemented merely because it is parsed. A feature
is implemented when its behavior is wired end to end and covered by a behavioral
test against a defined contract, preferably Portage itself.

## Executive conclusion

Arise has a promising repository, indexing, query, parsing, and orchestration
foundation. It is not currently close to emerge-equivalent for installing or
maintaining a Gentoo system.

| Area | Current assessment |
|---|---|
| Repository synchronization | Functional foundation |
| Metadata indexing | Fast, but resolver schema is incorrect |
| Search and installed queries | Useful and fast |
| Atom and metadata parsing | Substantial foundation |
| Dependency resolution | Prototype, not Portage-correct |
| Portage configuration/profile evaluation | Partial and disconnected |
| Ebuild execution | Not implemented |
| Source build pipeline | Generic make/autotools prototype |
| Installation | Resolver plan is not connected to execution |
| Merge safety | Unsafe prototype |
| Uninstall, depclean, prune | Presentation only |
| Binary packages | Partial XPAK code, not integrated |
| Resume and recovery | State serialization only |
| Concurrent builds | Worker pool, not dependency-aware |
| Tests | Many unit tests, insufficient behavioral coverage |

## Critical findings

### A-01: `arise install` does not execute its plan

`runResolve` prints a plan, saves resume state, and returns. It does not invoke
source builds, binary extraction, merge, blocker removal, or world updates.

Evidence: `cmd/arise/install.go`, after `SaveResume`.

### A-02: the metadata index discards versions and repository identity

Repository records are keyed by category/package. Every version and every
repository provider writes the same key. Concurrent ingestion can therefore
make the selected record nondeterministic.

Consequences include incomplete candidate sets, incorrect overlay precedence,
lost slots, unreliable masking/keyword decisions, and ineffective backtracking.

Evidence: `internal/ingest/ingest.go`, `encodeKey(entry.Key())`.

### A-03: indexed repository packages are treated as installed

`graph.BuildParallel` reads all `pkg:` database entries as installed metadata,
marks their graph nodes installed, and adds them to `InstalledAtoms`. Repository
metadata and VDB state are not modeled separately.

This invalidates upgrade detection, dependency satisfaction, noreplace,
changed-use/deps, depclean, prune, and action selection.

Evidence: `internal/graph/graph.go`, `BuildParallel`.

### A-04: Arise does not execute ebuild or eclass functions

The current phase runner performs generic archive extraction, `./configure`,
`make`, and `make install`. It does not source the selected ebuild or its
inherited eclasses. Most package lifecycle phases are explicit no-ops.

The correct direction is a Go-controlled, EAPI-aware Bash execution boundary,
not an attempt to reinterpret arbitrary ebuild Bash as Go.

Evidence: `internal/phase/phase.go` and `internal/rebuild/rebuild.go`.

### A-05: merge is not safe for a live system

Merge writes directly into the live root and creates VDB state before the
operation is known to succeed. Collision detection exists but is not wired.
There is no transaction journal, rollback, CONFIG_PROTECT, replacement
unmerge, ownership/xattr/capability preservation, complete VDB metadata, or
preserved-libs integration.

Evidence: `internal/merge/merge.go`; no production caller of
`merge.CheckCollisions`.

### A-06: removal commands do not remove packages

`uninstall` prints a path. `depclean` and `prune` print calculated removals.
None calls the internal unmerge primitive.

Evidence: `cmd/arise/uninstall.go` and `cmd/arise/depclean.go`.

### A-07: resolver inputs and semantics are incomplete

Known missing or incomplete behavior includes:

- complete per-version and per-repository candidates;
- repository priority and `::repository` constraints;
- profile and repository masks;
- full atom matching for package configuration;
- USE_ORDER, USE_EXPAND, implicit USE and ABI flags;
- profile use.force/use.mask and package/stable variants;
- correct REQUIRED_USE and LICENSE expression evaluation;
- virtual/provider selection;
- blockers, slots, subslots, circular dependencies, and rebuild triggers;
- any-of choice quality and genuine backtracking;
- installed metadata versus current ebuild metadata;
- Portage-compatible autounmask proposals.

The live `net-im/signal-desktop-bin` comparison successively exposed atom,
IUSE default, keyword, and ABI conditional discrepancies.

### A-08: profile parsing is not used by production resolution

`internal/profile` parses useful profile state, but production commands do not
load it. The resolver therefore lacks the active profile's defaults, system
set, USE masks/forces, and inheritance.

### A-09: parallel builds are not dependency-aware

A topologically sorted slice is sent to an ordinary worker pool. A dependent
can start before its dependency completes. Correct concurrency requires a DAG
ready queue and completion-driven release of dependents.

Evidence: `internal/rebuild/rebuild.go`, `RebuildPackagesParallel`.

### A-10: load-average limiting is not wired

The CLI creates a load-control context, but no production worker calls its
`Wait` method. `--load-average` has no effective build behavior.

### A-11: binary package support is not emerge-equivalent

The XPAK-oriented library is not connected to install execution. Modern Gentoo
GPKG, Packages indexes, signatures, build IDs, multi-instance packages, and
end-to-end `-k/-K/-g/-G/-b/-B` behavior remain absent.

### A-12: fetching is insufficient for the Gentoo repository

Only HTTP and HTTPS are implemented. `mirror://` and FTP fail. Manifest digest
verification, GENTOO_MIRRORS, distfile reuse, fallback ordering, RESTRICT,
pkg_nofetch, fetch-command configuration, and VCS fetchers are incomplete.

### A-13: several FEATURES are explicit stubs

Sandbox, usersandbox, network/pid/ipc sandbox, and fakeroot only log stub
messages. Collision protection, config protection, and preserve-libs are not
integrated into merge.

### A-14: resume state does not track completed execution

Resume JSON is written, but the normal install path never executes packages or
marks entries complete. It is a saved plan rather than a recovery mechanism.

### A-15: test volume does not prove package-manager correctness

There are many useful unit tests. The integration suite primarily checks atom,
version, and metadata parsing. It does not prove parity for candidate
visibility, effective USE, complete dependency plans, build execution, merge,
unmerge, binary packages, or recovery.

`go vet ./...` also reports two append-with-no-values issues in
`internal/phase/phase.go`.

## Concurrency assessment

The low-level concurrency foundation is promising. Walker, ingestion, graph,
rebuild, and sync packages pass focused race-detector tests. Concurrency must be
made deterministic at the system level:

1. Parse immutable CPV records in parallel.
2. Apply repository/profile precedence deterministically.
3. Resolve from a stable snapshot.
4. Fetch and build nodes from a dependency-aware ready queue.
5. Validate merge transactions concurrently where safe.
6. Commit filesystem mutations with explicit conflict control.

Resolution itself does not need to be broadly parallel. Candidate preparation,
metadata evaluation, fetch, build, hashing, and validation are better targets.

## Desired architecture

Arise should be divided conceptually into these layers:

1. **Filesystem adapters** — repositories, repos.conf, profiles, `/etc/portage`,
   VDB, world, distfiles, binpkg indexes.
2. **Immutable state snapshot** — every CPV, repository precedence, installed
   state, effective configuration inputs, ownership data.
3. **Derived package view** — visibility, effective USE, masks, licenses,
   dependency expressions, rebuild state.
4. **Planner** — deterministic dependency solution and ordered transaction.
5. **DAG scheduler** — concurrent fetch/build with resource constraints.
6. **Ebuild execution ABI** — controlled Bash subprocesses and EAPI helpers.
7. **Transaction engine** — validated merge/unmerge, journal, rollback, VDB and
   world commit.
8. **Presentation/API layer** — human output, stable JSON, search and queries.

BadgerDB remains an acceleration layer. Every record must be reproducible from
filesystem truth and carry an index/schema version.

## Definition of emerge parity

Arise may claim emerge parity for an operation only when:

- the same visible candidates are identified;
- the same effective configuration is calculated;
- the same dependency closure and blockers are produced;
- the same install/remove intent is produced, allowing documented deliberate
  improvements;
- the relevant EAPI phases execute correctly;
- the resulting filesystem and VDB state are Portage-readable;
- interruption is recoverable;
- differential tests cover representative real packages and adversarial
  fixtures.

## Definition of performance success

Performance comparisons must run on the same host, repository snapshot,
profile, Portage configuration, installed package state, warm/cold cache mode,
and requested operation. Every benchmark must also assert that Arise and
Portage produced equivalent results; a faster incorrect result does not count.

Arise should target order-of-magnitude improvements where indexing and an
in-process state model provide structural leverage, especially:

- search and installed-package queries;
- warm dependency planning and repeated plan variants;
- repository change ingestion;
- candidate visibility and effective USE evaluation;
- parallel fetch and independent package builds;
- resume/recovery startup and plan explanation.

Operations dominated by compiling one package cannot promise an
order-of-magnitude wall-clock improvement. In those cases Arise must reduce
orchestration overhead, overlap safe work, avoid duplicated work, and reach the
hardware/resource limit more efficiently than emerge.

Performance reports must include at least median, p95, peak memory, CPU time,
I/O volume, cache state, concurrency, and result-equivalence status. Thresholds
belong in versioned benchmark policy rather than being selected after results
are observed.
